Architecture Decision Records
Every significant decision.
Every alternative documented.

All architecture decisions made in the design of The Autonomous Enterprise — core platform decisions, ML design decisions, infrastructure decisions, and module-specific decisions. Each record states the context, the decision, the alternatives considered, and the consequences.

Core Platform
Foundation decisions — Phase A through Phase D.
ADR-001Salesforce Developer Edition REST API over production Salesforce credentials for integration validation
Status: AcceptedPhase: Phase AContext: ClaraVis Salesforce integration
The Salesforce integration layer for CCAI Sales Agent, ContractGuard, and RevRec AI must be validated against a real Salesforce environment before production credentials are involved. Developer Edition provides a permanent, free Salesforce org with full API access and standard objects (Account, Opportunity, Contract, Case, Product2, Pricebook). All integration patterns — OAuth 2.0, REST API calls, object creation, Activity logging — are validated in Developer Edition before any production deployment.
Alternative considered: Salesforce sandbox (requires existing production org). Rejected: introduces dependency on ClaraVis's Salesforce administration for a portfolio project.
Documented: Page 03 ADM Phase A · Used by: M-01 CCAI Sales Agent · M-02 ContractGuard · M-03 RevRec AI
ADR-002GCP alongside Salesforce and SAP — augmentation not replacement
Status: AcceptedPhase: Phase A
The AE is the orchestration and intelligence layer that sits above Salesforce and SAP. It never replaces them. Salesforce remains the system of record. SAP remains the ERP. This decision eliminates the most common enterprise AI adoption failure mode: the system migration risk. ClaraVis's existing Salesforce and SAP implementations are not touched, re-platformed, or migrated.
Alternative considered: Replace Salesforce CPQ with a custom AE CPQ layer. Rejected: eliminates ClaraVis's existing 15-year Salesforce investment and introduces unacceptable migration risk.
Documented: Page 03 ADM Phase A · Referenced: Page 08 GTM — adoption risk
ADR-003Cloud Run over GKE for stateless agent services
Status: AcceptedPhase: Phase D
Cloud Run's per-request billing model, scale-to-zero capability, and request-driven execution are optimal for the AE's agent workloads — short-duration, event-triggered, stateless request handlers. Cloud Run handles the FinRisk Sentinel streaming agent (always-on, min 2 instances), the GreenOps agent (always-on, min 1 instance), the ContractGuard agent, and the RevRec AI agent. GKE is reserved for GKE Autopilot batch ML workloads that require GPU access and longer-running jobs.
Alternative considered: All agents on GKE Standard. Rejected: node pool management overhead, instance-idle billing for low-frequency agents.
Documented: Page 03 ADM Phase D · Architecture: Page 07 Infrastructure
ADR-004Firestore for agent state and HITL audit over Cloud Spanner or BigQuery
Status: AcceptedPhase: Phase D
Firestore's document model matches the AE's agent state structure natively — a conversation session, a HITL checkpoint, and a contract analysis result are all naturally document-shaped. Firestore's strong consistency, real-time listeners, and CMEK support make it the correct choice for HITL state that must be written atomically and read immediately by the reviewing human's UI. BigQuery exports of Firestore HITL records provide the long-term audit trail.
Alternative considered: Cloud Spanner for relational HITL records. Rejected: HITL data is not relational — it's document-shaped state with nested arrays of reviewer actions.
Documented: Page 03 Phase D · Used by all HITL checkpoints: Page 04
ADR-005SHAP TreeExplainer over LIME for the XAI explanation layer
Status: AcceptedPhase: Phase D
SHAP TreeExplainer produces exact, deterministic attributions for tree-based models (XGBoost, Isolation Forest). LIME produces approximations that vary between runs. EU AI Act Article 13 requires reproducible explanations — an auditor who queries the BigQuery SHAP record six months after a classification must see the same values the human reviewer saw at the time of decision. LIME's approximation-based approach is architecturally inconsistent with an immutable audit trail.
Alternative considered: LIME (Local Interpretable Model-agnostic Explanations). Rejected: non-deterministic — fails the EU AI Act Art. 13 immutable audit requirement.
Documented: Page 03 Phase D · Applied: Page 06 ML Engineering
ADR-006Pub/Sub as the integration event bus over direct HTTP inter-service calls
Status: AcceptedPhase: Phase D
Pub/Sub decouples the AE from Salesforce and SAP outages. A Salesforce maintenance window or SAP batch job does not cascade into AE agent failures — the event remains in the Pub/Sub topic until the AE agent is ready to process it. Pub/Sub also provides the audit trail of event delivery, the schema validation hook for Data Governance (M-08), and the fan-out capability that allows multiple consumers (FinRisk Sentinel, Data Governance, the Strategy Dashboard feed) to receive the same event without coordination.
Alternative considered: Direct HTTP calls from Salesforce webhooks to Cloud Run. Rejected: tight coupling — Salesforce webhook failure during AE downtime causes permanent event loss.
Documented: Page 03 Phase D · Used by: M-08 Data Governance · all three ae- topics
Agent Design
Multi-agent orchestration decisions — Phase Agent Design.
ADR-007Google ADK over LangGraph or CrewAI for multi-agent orchestration
Status: AcceptedPhase: Agent Design
ADK provides native integration with CCAI (required for the CCAI Sales Agent voice and web chat channels), Dialogflow CX (conversation routing), Vertex AI (inference endpoints), and Cloud Run (deployment). LangGraph and CrewAI require custom adapters for each of these GCP services. ADK's A2A protocol (ADR-008) is a first-class typed inter-agent communication standard. For a 100% GCP portfolio architecture, native integration eliminates adapter maintenance burden and reduces operational complexity.
Alternative considered: LangGraph (graph-based agent orchestration). Rejected: no native CCAI/Dialogflow CX integration, framework-specific agent communication protocol.
Documented: Page 05 Agent Swarm · Applied: M-01 CCAI Sales Agent
ADR-008A2A protocol over direct HTTP for inter-agent communication
Status: AcceptedPhase: Agent Design
A2A defines a typed message contract between agents. The Orchestrator sends a structured task message and receives a structured response. If a sub-agent's response schema changes, the build fails at A2A schema validation rather than at runtime in a live conversation. A2A also enables agent replaceability — the Orchestrator depends on the contract, not the implementation. Sub-agents can be upgraded, A/B tested, or replaced without changing the Orchestrator.
Alternative considered: Direct HTTP calls with untyped JSON. Rejected: schema changes cause runtime failures in production, not build-time failures in development.
Documented: Page 05 Agent Swarm · Applied: M-01 CCAI Sales Agent
ADR-009Firestore over Redis for agent state and HITL audit trail
Status: AcceptedPhase: Agent Design
Redis is appropriate for ephemeral session caching. HITL audit records are not ephemeral — they are immutable compliance documents that must be queryable for 7 years. Firestore provides native CMEK, strong consistency for concurrent HITL reviewer decisions (optimistic locking in FinRisk Sentinel's dual-reviewer HITL-08), real-time listeners for the HITL UI, and native BigQuery export for long-term audit storage.
Alternative considered: Redis for agent session state + BigQuery for HITL records (two separate stores). Rejected: operational complexity of two stores for the same data lifecycle.
Documented: Page 05 Agent Swarm · Relied on by all HITL checkpoints
ML Design
Model architecture decisions — Phase ML Design.
ADR-010XGBoost over neural network for RevRec AI and ContractGuard risk scoring
Status: AcceptedPhase: ML Design
EU AI Act Article 13 requires reproducible explanations. XGBoost's TreeExplainer produces exact, bit-for-bit reproducible SHAP values. Neural network SHAP (DeepExplainer / KernelExplainer) produces approximations that vary between runs — an approximation in an immutable audit trail is an architectural contradiction. XGBoost also performs competitively at the training dataset sizes available (4,800 contracts for RevRec AI, 12,400 labelled clauses for ContractGuard) and is less prone to overfitting than deep models at this scale.
Alternative considered: MLP neural network. Rejected: KernelExplainer SHAP approximations — non-deterministic, violates EU AI Act Art. 13 immutable audit requirement.
Documented: Page 06 ML Engineering · Applied: M-03 RevRec AI · M-02 ContractGuard
ADR-011Isolation Forest over autoencoder for anomaly detection (FinRisk Sentinel and Asset IQ)
Status: AcceptedPhase: ML Design
Two reasons: (1) Isolation Forest's decision-tree structure is directly compatible with TreeExplainer — exact SHAP attributions in milliseconds, essential for FinRisk Sentinel's <5-minute alert path. Autoencoder SHAP requires KernelExplainer approximations that are too slow for real-time scoring. (2) Both applications are unsupervised — no labelled anomaly examples exist. Isolation Forest is designed for this scenario (contamination parameter for expected anomaly rate). Autoencoders trained on normal data also work but require careful architecture design to avoid learning the identity function.
Alternative considered: Autoencoder-based anomaly detection. Rejected: KernelExplainer SHAP too slow for streaming; architecture complexity for normal-only training data.
Documented: Page 06 ML Engineering · Applied: M-04 FinRisk Sentinel · M-05 Asset IQ
ADR-012Vertex AI Pipelines over self-managed Kubeflow Pipelines
Status: AcceptedPhase: ML Design
Vertex AI Pipelines is a managed service — no pipeline orchestrator infrastructure to provision, patch, or scale. It integrates natively with Vertex AI Model Registry (model versioning for FDA change control), ML Metadata store (lineage for EU AI Act Article 11), and Feature Store (training data provenance). The operational overhead of running a Kubeflow Pipelines cluster for a portfolio-scale deployment is not justified by any capability advantage.
Alternative considered: Self-managed Kubeflow Pipelines on GKE. Rejected: infrastructure management overhead with no capability advantage at portfolio scale.
Documented: Page 06 ML Engineering
Infrastructure Design
GCP platform decisions — Phase Infra Design.
ADR-013Shared VPC over separate VPCs per module
Status: AcceptedPhase: Infra Design
Separate VPCs per module creates an O(n²) peering mesh with 8 modules that approaches GCP peering limits and is operationally complex. Shared VPC centralises network management in the host project — module SAs cannot modify network topology. Private Service Connect endpoints are provisioned once in the shared VPC and consumed by all modules. Security isolation between modules is maintained at the IAM and VPC-SC layer, not the network boundary layer.
Alternative considered: One VPC per module. Rejected: O(n²) peering mesh, module SAs with network admin rights, 8 separate PSC configurations.
Documented: Page 07 Infrastructure
ADR-014Cloud Armor over third-party WAF (Cloudflare, Imperva)
Status: AcceptedPhase: Infra Design
Third-party WAFs route traffic outside the GCP network before it reaches Cloud Load Balancer — any traffic routing outside GCP before the VPC-SC perimeter is a data sovereignty risk requiring legal review under ClaraVis's GDPR obligations. Cloud Armor integrates natively with Cloud Load Balancer and Security Command Center. Cloud Armor Adaptive Protection (ML-based DDoS detection) is included in Cloud Armor Enterprise — comparable capability without the data routing concern.
Alternative considered: Cloudflare WAF. Rejected: traffic routing outside GCP network before VPC-SC perimeter — data sovereignty risk under GDPR.
Documented: Page 07 Infrastructure
ADR-015GKE Autopilot over GKE Standard for batch ML workloads
Status: AcceptedPhase: Infra Design
GKE Standard requires node pool management — machine type selection, node lifecycle management, OS patching. Autopilot abstracts all of this — Vertex AI Pipelines submits pod specs, Autopilot provisions the right nodes. Autopilot's per-pod billing is more cost-efficient for intermittent batch workloads than Standard's per-node billing. Autopilot automatically applies GKE hardening (no SSH access, enforced container security context, Workload Identity pre-configured).
Alternative considered: GKE Standard with managed node pools. Rejected: node management overhead, per-node billing for intermittent batch jobs, manual hardening required.
Documented: Page 07 Infrastructure · Used by: M-05 Asset IQ · M-06 GreenOps
Go-to-Market
Adoption strategy — Phase GTM Design.
ADR-016Phased adoption (H1/H2/H3) over big-bang full-suite deployment
Status: AcceptedPhase: GTM Design
ClaraVis has a hard regulatory deadline (Q2 2026 EU AI Act review), limited internal change management capacity, two complex legacy system integrations, and 9 stakeholders with different adoption readiness levels. Full suite deployment in a single programme would require all of these to be addressed simultaneously. H1 delivers compliance infrastructure before the review. H2 delivers core business modules. H3 delivers the full suite. Each horizon is independently valuable — ClaraVis can pause after H1 or H2 and retain the value already delivered.
Alternative considered: Full AE suite as a single programme. Rejected: EU Act deadline cannot wait; change management load across 9 stakeholders is untenable; no partial value if programme stalls.
Documented: Page 08 GTM Strategy
Module-Specific Decisions
Per-module ADRs — each documented on its module page.
ADR-SA01Turn-11 escalation boundary for CCAI Sales Agent
5 turns is insufficient for BANT + CPQ. 20 turns is poor sales experience. 11 is the boundary where BANT is complete, BOM is configured, pricing is presented, and the AE enters at the natural handoff point where technical discussion begins.
M-01 CCAI Sales Agent — ADR-SA01
ADR-SA02Salesforce Opportunity created at turn 6, not at HITL-01 escalation
The AE's first action after reading the briefing is to open Salesforce. If the Opportunity doesn't exist, the AE wastes 30–90 seconds creating it — exactly the administrative task the agent eliminates.
M-01 CCAI Sales Agent — ADR-SA02
ADR-CG01Two-pass architecture (Document AI → Gemini) for ContractGuard
Gemini-only extraction is unstructured, expensive per clause, and breaks on unusual contract formats. Document AI provides deterministic structured extraction; Gemini provides semantic reasoning over the full document. Each pass does what it is optimised for.
M-02 ContractGuard — ADR-CG01
ADR-CG02Vertex AI Vector Store over BigQuery vector search for ContractGuard precedents
BigQuery VECTOR_SEARCH has no ANN index — latency degrades as corpus grows. Vertex AI Vector Store uses ANN and returns top-k in under 100ms. First-class integration with Feature Store and Gemini embedding API.
M-02 ContractGuard — ADR-CG02
ADR-R01SAP write requires hitl_id as a mandatory function parameter
Application-level checks can be bypassed by a bug or future code change. The SAP write guard is in the function signature, not in conditional logic. A developer cannot accidentally remove the HITL requirement without explicitly changing the function signature.
M-03 RevRec AI — ADR-R01
ADR-R02HITL-04 required for every RevRec AI classification — no confidence threshold exception
EU AI Act Annex III does not distinguish by confidence level. Auto-approving high-confidence classifications removes the feedback loop that builds Finance Controller trust and produces training signal from overrides.
M-03 RevRec AI — ADR-R02
ADR-FR01Streaming Pub/Sub scoring over scheduled BigQuery batch for FinRisk Sentinel
A 15-minute batch window is unacceptable for a 1-hour HITL SLA. The streaming architecture detects and alerts within 18 seconds of a payment event. BigQuery SQL cannot call a Vertex AI endpoint synchronously.
M-04 FinRisk Sentinel — ADR-FR01
ADR-FR02Dual-reviewer HITL-08 over single-reviewer for high-severity financial alerts
Separation of duties for financial fraud alerts. EU AI Act Article 14 requires oversight proportionate to the risk. Matches the four-eyes principle already applied to financial authorisations above a threshold at ClaraVis. Optimistic lock handles concurrent decisions correctly.
M-04 FinRisk Sentinel — ADR-FR02
ADR-AQ01GKE Autopilot for batch RUL over Cloud Run for Asset IQ
Cloud Run max timeout 60 minutes — insufficient margin for a 45-minute batch job. RUL job requires GPU (A100) which GKE Autopilot provisions natively. Per-pod billing is optimal for one long infrequent job; Cloud Run per-request billing is optimal for many short frequent requests.
M-05 Asset IQ — ADR-AQ01
ADR-AQ02Unified Pub/Sub schema over per-region API adapters for Asset IQ ingestion
Cross-regional fleet analytics (HITL-07) require a single BigQuery query across all regions — impossible without a common schema. Data Governance (M-08) enforces the unified schema at the ingestion gate. The unified schema makes ADR-AQ02 enforceable at runtime, not just as a design convention.
M-05 Asset IQ — ADR-AQ02 · M-08 Data Governance
ADR-GO01±6 hour deferral window for GreenOps carbon-aware scheduling
±1h rarely spans a low-carbon trough. ±24h affects model freshness. Analysis of 90 days of europe-west3 Carbon Footprint API data: low-carbon window occurs within 6 hours 73% of the time. 6-hour deferral on a weekly retraining job = 0.4% interval increase — statistically indistinguishable from normal variation.
M-06 GreenOps — ADR-GO01
ADR-GO02GCP Carbon Footprint API over third-party APIs (Electricity Maps, WattTime) for GreenOps
Third-party APIs require outbound internet calls — a VPC-SC network egress path that requires CISO approval. GCP's API is available within the perimeter. Consistent with GCP billing carbon reporting, ensuring internal CSRD reporting consistency.
M-06 GreenOps — ADR-GO02
ADR-DG01TFX ExampleValidator over custom JSON schema validation for Data Governance
TFX is stateful — it detects distributional drift, not just structural violations. Integrates natively with Vertex AI Pipelines ensuring same schema enforced at training and serving. Great Expectations integration produces living data quality documentation satisfying EU AI Act Article 11.
M-08 Data Governance — ADR-DG01
ADR-DG02Quarantine-then-review over reject-on-arrival for schema violations in Data Governance
Sensor data cannot be re-sent — Pub/Sub delivery window is finite. A schema violation often indicates a legitimate upstream system update, not corrupted data. Quarantine preserves the raw record for reprocessing once the mapping is confirmed. Reject-on-arrival causes permanent data loss.
M-08 Data Governance — ADR-DG02
ADR-SD01Looker Studio over custom React dashboard for Strategy Dashboard
Native BigQuery connector, GCP IAM integration, no separate backend or authentication layer. Correct for the executive audience who consume dashboards in meetings, not in the developer console. Custom React UX investment is better spent on HITL interfaces where UX directly affects operational decisions.
M-07 Strategy Dashboard — ADR-SD01
ADR-SD02Materialised BigQuery views over live queries for Strategy Dashboard
Live queries compete with operational writes for BigQuery slots. Per-panel refresh cadences (5min to 1h) match actual freshness requirements — fleet panel does not need 5-minute refreshes. Materialised view definitions are the auditable specification of what the dashboard shows.
